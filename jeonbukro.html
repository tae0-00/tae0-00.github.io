M-01

메인페이지 — GeoJSON → SVG 좌표 변환

전북 행정구역을 클릭해 지역별 여행지로 이동하는 인터랙티브 지도입니다.

통계청 행정경계 GeoJSON에서 전북 지역만 추출하고, 라이브러리에 의존하지 않고 위경도 좌표를 SVG 화면 좌표로 직접 변환해 지도를 그렸습니다.

위도는 북쪽이 클수록 큰 값이지만 화면 y축은 아래로 갈수록 커지므로, y좌표를 반전 처리해 지도가 뒤집히지 않도록 했습니다. 지역 클릭 시 지역명을 코드로 변환해 해당 여행지 목록으로 이동합니다.

계절별 메인 화면 자동 변경

같은 사이트라도 봄에는 봄에 어울리는 여행지를, 겨울에는 겨울 분위기를 보여줘 방문 시점에 맞는 여행 감성을 자연스럽게 전달하도록 구현했습니다.

M-03

여행지 목록 — 필터 상태 유지 & 낙관적 업데이트

카테고리·지역·정렬·검색을 조합해 여행지를 탐색하는 목록 페이지입니다.

필터·정렬·페이지 상태를 URL 파라미터로 관리해 뒤로가기를 해도 필터가 유지되도록 했습니다. 찜 여부 조회에 필요한 userId는 URL에 노출하지 않고 JWT에서 직접 추출해 보안과 사용성을 함께 고려했습니다.

찜 기능은 API 응답을 기다리지 않고 하트와 카운트를 화면에 먼저 반영하는 낙관적 업데이트로 구현해 반응 속도를 높였습니다.

M-04

여행지 상세 — 카테고리 분기 · 지도 · fallback

공공 관광 API는 카테고리(contentTypeId)마다 응답 필드 구조가 전혀 달랐습니다.

이를 백엔드 변경 없이 수용하기 위해 typeId 기준으로 상세 조회를 분기하고, 프론트에서도 해당 필드만 골라 렌더링했습니다. 새로운 장소 유형이 추가돼도 분기만 늘리면 대응할 수 있습니다.

위경도 좌표를 카카오맵 객체로 변환해 마커·길찾기를 연동하고, 이미지가 하나도 없는 여행지는 카테고리별 기본 이미지(fallback)로 대체했습니다.

C-01

역사 코스 목록 — 공공/자체 데이터 분리

전북 역사 여행 코스를 카드 형태로 보여주는 목록 페이지입니다.

장소 정보(관광지·지역·이미지)는 공공 API에서 가져와 DB에 저장하고, 코스 구성(순서·묶음·설명)은 직접 설계해 별도로 관리했습니다. 공공 데이터와 자체 제작 데이터를 분리해 한쪽이 바뀌어도 다른 쪽에 영향이 가지 않도록 유지보수성을 높였습니다.

C-02

역사 코스 상세 — 동선 자동 판별 · 지도 시각화 · iframe 재사용

코스의 경유지 간 이동 정보를 자동으로 계산하고 지도에 시각화합니다.

카카오 Directions API로 도보·차량 시간을 받아 임계값(15분) 기준으로 이동수단을 자동 판별하고, 호출이 실패하면 두 좌표의 직선거리를 직접 계산(Haversine)하는 폴백을 넣어 API가 불안정해도 동선 정보가 끊기지 않도록 했습니다.

각 관광지를 마커로 표시하고 DAY별로 다른 색의 경로선(Polyline)을 연결했으며, 전체 장소를 포함하는 영역(bounds)을 계산해 지도 확대 수준을 자동 조정했습니다. 또한 이미 만든 여행지 상세 페이지를 iframe으로 모달에 재사용해, 코스 페이지를 벗어나지 않고 상세를 확인하도록 구현했습니다.

역사 코스를 직접 등록·수정·관리하는 페이지입니다.

신고 관리 — 승인 시 리뷰 자동 숨김 연동

신고를 승인하면 신고 상태를 처리완료로 바꾸는 동시에 대상 리뷰를 자동으로 숨김 처리해, 관리자가 두 번 작업하지 않아도 신고와 리뷰 상태가 항상 일치하도록 연동했습니다.

A-06

여행지 이미지 관리 — 리뷰 사진을 대표 이미지로

공공 API(TourAPI)에서 받아온 데이터 중 이미지가 NULL인 여행지가 많아, 목록·상세가 비어 보이는 문제가 있었습니다.

FIRST_IMAGE가 비어 있는 여행지만 필터링해 보완 대상을 선별하고, 사용자가 올린 리뷰 이미지를 관리자가 검토해 공식 여행지 이미지로 등록할 수 있게 했습니다. 대표 이미지가 없는 여행지는 등록된 리뷰 이미지를 자동으로 대표 이미지로 설정해, 별도 수집 없이 콘텐츠를 풍부하게 유지했습니다.

CASE 01찜 상태 표시 불안정 — Race Condition 해결
● 문제

여행지 목록에서 찜한 하트가 새로고침·뒤로가기 때마다 사라졌다 나타났다 하며 불안정했습니다. 백엔드와 상세 페이지는 정상이었습니다.

▲ 원인

JWT 파싱이 끝나기 전에 목록 API가 먼저 호출돼 userId가 null인 채로 요청됐고, 서버가 "찜 없음"으로 응답했습니다. userId 비동기 초기화 타이밍으로 인한 Race Condition이었습니다.

✓ 해결

userId가 확정되기 전에는 목록 조회를 막고, 비로그인 사용자도 확정 fetch가 돌도록 처리해 항상 정확한 찜 상태가 렌더되게 했습니다.

Race Condition비동기 초기화useEffect 의존성JWT
CASE 02외부 API 장애 대비 — Haversine 폴백
● 문제

역사 코스의 동선 계산을 외부 지도 API에 의존하다 보니, API 장애 시 동선 정보가 통째로 끊길 위험이 있었습니다.

▲ 원인

정상 응답만 가정한 설계라, 외부 의존성의 실패 경로가 비어 있었습니다.

✓ 해결

호출 실패 시 두 좌표의 직선거리를 직접 계산하는 Haversine 폴백을 넣어, API가 불안정해도 동선이 끊기지 않게 했습니다.

CASE 03방문자 중복 집계 방지 — 메모리 관리
● 문제

같은 사용자가 여러 번 접속하면 방문자 수가 부풀려져, 관리자 지표를 신뢰할 수 없었습니다.

▲ 원인

방문 이벤트를 단순 누적만 하고, 같은 사용자를 식별·중복 제거하는 구조가 없었습니다.

날짜별 Set에 회원 ID·IP 식별자를 저장해 중복을 제거하고, 지난 날짜 데이터는 자동 제거해 메모리가 쌓이지 않게 했습니다.
