// SHOP & COMMUNITY
S-01

메인페이지 — 사용자 맞춤 추천 분기

회원의 반려동물 정보(종류·연령)를 기반으로 맞춤 상품을 추천하는 기능입니다.

모든 사용자에게 같은 상품을 노출하지 않기 위해 로그인·펫 등록 여부에 따라 추천 전략을 분기했습니다. 펫 정보가 있으면 종류·연령에 맞는 판매량 상위 상품을, 없거나 비로그인 시에는 전체 인기 상품을 노출합니다.

펫 타입·연령·카테고리 조건에 따라 쿼리가 동적으로 구성되도록 설계했고, 정보가 없는 사용자에게도 빈 화면 대신 기본 추천을 제공하도록 처리했습니다.

조건 분기동적 쿼리추천 로직
S-02

상품 목록 — MyBatis 동적 SQL 필터·정렬

검색어·반려동물 유형·카테고리·정렬 조건을 조합해 상품을 조회하는 기능입니다.

사용자가 여러 필터를 동시에 선택하거나 일부만 선택할 수 있도록, MyBatis 동적 SQL로 입력된 조건이 있을 때만 쿼리에 추가되게 구현했습니다. 검색어·펫 타입·카테고리는 <if>로 분기하고, 정렬은 <choose>로 가격순·조회순·최신순을 선택하도록 처리해, 필터 조건을 유지한 채 정렬까지 함께 적용되도록 했습니다.

MyBatis<if> / <choose>다중 필터
S-03

상품 상세 — 재고 기반 품절·구매 제어

재고 수량을 기준으로 품절 여부를 표시하고 구매를 제어하는 기능입니다.

재고가 없는 상품인데도 구매 버튼이 눌리면 잘못된 주문이 발생할 수 있다는 문제가 있었습니다. 이를 해결하기 위해 DB의 재고 수량(productStock)을 기준으로 품절을 판단하고, 재고가 0 이하면 품절 상태 표시 + 구매 버튼 disabled를 동시에 적용해 주문 자체가 불가능하도록 제어했습니다.

재고 검증JSTL <c:if>
S-04

커뮤니티 — 게시판 분기 · 조회수 중복 방지 · 권한 검증

3개 게시판으로 구성된 커뮤니티의 등록·상세·수정·삭제와 댓글·신고 기능입니다.

게시판 유형에 따라 카테고리 선택 UI를 동적으로 분기하고, 인기/최신 게시글을 ROWNUM 기준으로 출력했습니다. 같은 사용자가 새로고침할 때마다 조회수가 오르는 문제는 쿠키 기반 조회수 중복 방지(유효기간 하루)로 해결했습니다.

수정·삭제 권한은 화면에서 버튼을 숨기는 것에 그치지 않고 서버에서도 작성자 여부를 다시 검증해 직접 요청까지 차단했습니다. 댓글 신고는 신고 유형을 코드에 고정하지 않고 별도 테이블(REPORT_TYPE)로 분리해, 유형이 늘어나도 코드 수정 없이 확장할 수 있도록 설계했습니다.

★ 핵심 작업 · KEY CONTRIBUTION

주문 부분취소 — ORDER_DETAIL 설계 변경

개발 중, 주문 취소가 주문 전체 단위로만 가능해 상품별 개별취소가 안 되는 문제를 발견했습니다. 원인은 취소 상태를 주문 단위로만 관리해 상품별 상태를 담을 구조가 없다는 점이었습니다.

이미 확정된 DB 구조를 바꾸는 일이라, ORDER_DETAIL에 상품별 상태 컬럼(ORDERED / CANCELLED)을 추가하는 설계 변경을 제안하고, 컬럼 추가로 깨지는 코드는 직접 책임지기로 하고 진행했습니다. 상태 기준이 주문→상품 단위로 바뀌면서 연결된 로직을 전부 다시 구현했습니다.

① 사용자
마이페이지 주문취소를 상품 단위로 받도록 수정
② 관리자
상품별 상태를 계산해 개별 취소·상태 변경 가능하도록 전면 수정
③ 배송비
취소되는 상품 단위로 귀책 판단 — 변심은 고객, 하자·지연은 판매자 부담

그 결과 한 주문에서 일부 상품만 취소해도 나머지 주문은 정상 유지되고, 주문 상태와 실제 상품 상태가 항상 일치하도록 데이터 정합성을 확보했습니다.

A-01

상품 등록 — 동적 카테고리 · 업체 모드 전환

상품 기본 정보와 대표·상세 이미지를 등록하고, 반려동물 유형·연령을 분류·추천에 활용하는 기능입니다.

카테고리는 값을 코드에 고정하지 않고 PRODUCT_CATEGORY 테이블에서 조회해 동적으로 출력했고, 업체 등록은 사용자 선택(companyMode)에 따라 기존 업체 선택과 신규 등록 UI가 전환되도록 처리했습니다.

동적 카테고리UI 모드 전환
A-02

상품 관리 — 판매 상태 즉시 전환

등록된 상품을 카테고리·상태·검색어 조건으로 조회하고 관리하는 페이지입니다.

PRODUCT_ACTIVE_YN 값을 기준으로 판매중·판매중지 상태를 표시해 관리자가 즉시 전환할 수 있도록 했고, 상태 변경 시 PRODUCT_ID를 함께 전달해 특정 상품만 정확히 반영되도록 처리했습니다. 수정 버튼을 누르면 기존 데이터를 조회해 수정 페이지에 미리 채워 보여주도록 구현했습니다.

상태 토글데이터 prefill
A-03

주문 관리 목록 — 주문 상태 동적 계산

전체 주문을 통합 조회·관리하는 페이지입니다. 기간·상태·키워드로 검색할 수 있습니다.

핵심은 주문 상태 계산 로직입니다. 상품별 취소가 가능한 구조이다 보니 주문 전체 상태를 하나로 표시하기 어려웠는데, ORDER_DETAIL의 상품별 취소 집계값(요청·승인·반려·전체 건수)과 배송 상태를 조합해 정상·부분취소 요청·부분취소 완료·전체취소 완료·부분취소 반려·배송중·배송완료를 동적으로 계산해 표시했습니다.

CASE 집계상태 동적 계산
A-04

주문 상세 · 취소 관리 — 상품별 처리 · 배송비 귀책

한 주문 안에서도 일부 상품만 취소하고 나머지는 정상 유지되도록, ORDER_DETAIL 기준으로 상품별 취소를 처리하는 페이지입니다.

취소 요청(PENDING) 중인 주문은 배송 상태를 함부로 바꿀 수 없도록 잠가 취소 처리와 배송 상태가 어긋나지 않게 제어했습니다.

핵심은 배송비 귀책 판단입니다. 단순 변심·주문 실수는 사용자가, 상품 불량·배송 지연은 판매자가 부담하도록 분기하고, 나아가 배송 진행 여부까지 고려해 배송 전 취소는 배송비를 부과하지 않고 배송이 시작된 뒤의 취소는 사유에 따라 부과·면제를 결정했습니다.

상품 단위 취소배송비 귀책 분기상태 잠금
A-05

댓글 신고 관리 — soft delete · 일괄 처리

신고된 댓글을 검토·처리하는 페이지입니다. 신고자·대상·유형·내용·상태를 조회하고, 원문까지 확인할 수 있습니다.

처리는 댓글을 실제로 삭제하지 않고 COMMENT_ACTIVE_YN 값을 'N'으로 바꿔 화면에서만 가리는 soft delete로 구현해, 데이터를 보존하면서 부적절한 댓글을 비노출했습니다. 신고 건이 많을 수 있어 단건 처리와 선택 일괄 처리를 분리하고, 일괄 처리는 REPORT_ID 목록을 받아 한 번에 비노출하도록 구현했습니다.

CASE 01 · 핵심주문 부분취소 — ORDER_DETAIL 구조 재설계
● 문제

주문 취소가 주문 전체 단위로만 가능해, 한 주문에 담긴 여러 상품 중 일부만 취소할 방법이 없었습니다. 사용자 관점에서 명백한 불편이었습니다.

▲ 원인

취소 상태를 주문 단위로만 관리해, 상품별 상태를 담을 구조 자체가 없었습니다.

✓ 해결

ORDER_DETAIL에 상품별 상태 컬럼을 추가하고, 마이페이지·관리자·배송비 귀책 로직을 전면 재구현해 데이터 정합성을 확보했습니다.
